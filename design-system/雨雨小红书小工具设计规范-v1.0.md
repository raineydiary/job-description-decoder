# 雨雨小红书小工具设计规范 v1.0

> YUYU Y2K PIXEL MINI-TOOL SYSTEM  
> 适用于雨雨后续的小红书小工具、轻游戏、测试器、模拟器和互动生成器。

![已定稿的移动端参考](../research/qa/jd-decoder-iphone-final-approved.png)

## 1. 设计定位

### 1.1 一句话定义

**把一个年轻人熟悉的现实焦虑，装进一台来自 Y2K 平行世界的小机器里，用好笑、直接、想截图的方式给出结果。**

### 1.2 核心受众

- 00 后、05 后，正在秋招、实习、选 Offer 或初入职场的用户。
- 他们不想读教科书，先被视觉和梗吸引，再从娱乐中拿走一点真实价值。
- 多数小工具是一次性体验，首要指标是“点开就懂、马上能玩、结果想分享”，而不是复购或复杂留存。

### 1.3 三条设计原则

1. **像一个真实的复古物件，不像一张 AI 卡片。** 优先使用 BB 机、掌机、收音机、售票机、老式电脑、转盘或盲盒机等有实体隐喻的交互容器。
2. **信息紧凑，但不拥挤。** 首屏必须看到工具是什么、主操作在哪里，并尽量露出一个可玩的次入口。
3. **抽象可以，空洞不可以。** 翻译、测试结果和吐槽必须对应真实语境，说到用户心里，不写泛化的“高效协作、赋能成长”式 AI 话术。

## 2. 视觉 DNA

### 2.1 风格关键词

`Y2K` · `像素` · `BB 机` · `复古掌机` · `半透明彩色塑料` · `LCD 屏` · `千禧贴纸` · `轻微粗糙` · `年轻互联网黑话`

理想效果是：**一眼像 2003 年生产、2026 年被 05 后重新发现的怪小玩意。**

### 2.2 禁用的默认 AI 感

- 不使用大面积苹果式毛玻璃、精致灰白卡片、软糖渐变或每个 AI 应用都相似的圆角 Dashboard。
- 不使用“高端、光滑、无菌”作为默认美学；允许硬边框、塑料感阴影、扫描线、螺丝和略显笨拙的机械结构。
- 不简单把内容放入一个白色容器；交互控件应该是世界观的一部分，例如“破译键”而不是普通的 Submit。

### 2.3 基础色盘

| 角色 | 色值 | 用法 |
| --- | --- | --- |
| 冰蓝机壳 | `#92C7DD` | 默认主机壳、大面积视觉识别 |
| 浅蓝高光 | `#C4E9EF` | 塑料内高光、底纹 |
| 墨蓝边线 | `#3B3859` | 外轮廓、按钮边、机器结构 |
| LCD 果绿 | `#C7ECB8` | 输入、结果和文本主屏 |
| 桃心粉 | `#F196D4` | 核心 CTA、问号、动效焦点 |
| 葡萄紫 | `#A17BD0` | 可换机壳、次按钮、复古魔幻感 |
| 黑酸绿 | `#454953` + `#A0F66C` | 暗色机壳与酸性高光 |
| 奶油黄 | `#F3DFA1` | 盲盒、纸贴、辅助信息 |

配色规则：

- 一个画面保持 **1 个主机壳色 + 1 个屏幕色 + 1 个高亮色 + 2–3 个贴纸色**。
- 色彩可以丰富，但按钮必须靠深色轮廓、阴影和明度差保持可读性。
- 不追求全页统一为一个精致渐变；应该像被用户自己换过壳、贴过贴纸的随身机器。

### 2.4 字体与文字层级

- 大标题、按键、状态字和 LCD 内容优先使用有中文覆盖的像素字体；整体不使用过度现代的无衬线大字。
- 小号免责说明、长段阅读文字可回退到 `PingFang SC / Microsoft YaHei`，避免小像素字长文难读。
- 建议层级：首页大标题 32–36px；机器名称 22–26px；核心结果 18–22px；按钮 16–18px；状态与说明 10–12px。

## 3. 布局与首屏

### 3.1 移动端基准

- 默认以 **402 × 874 CSS px** 的 iPhone Pro 竖屏视口做首轮验收，同时检查 360px 窄屏。
- 页面主容器建议左右留白 20px；窄屏降至 12px。触摸按钮高度不小于 44px，主 CTA 建议 50px 以上。
- 以 4px 为微调单位、8px 为布局网格。间距收紧时逐级从 20 → 12 → 8 → 4px 调整，不使用无规则小数。

### 3.2 首屏必须回答的三个问题

1. **这是什么？** 用一句小字 + 一句大标题说清楚，例如“JD 写得很漂亮 / 实际真相是？”
2. **我现在做什么？** 主输入和主 CTA 在第一屏内完整可见，不用阅读教程才能操作。
3. **还有什么好玩？** 尽量在首屏底部露出次入口，如 5 个盲盒、换壳或测试频道。

### 3.3 紧凑而不拥挤

- 先删除无价值的空白，再缩字；不用过小文字来强行塞满首屏。
- 次要装饰可以超出机壳边缘，但不能压住任何可点按钮、标题、序号或结果文字。
- 一个可交互区域与下一区域之间通常保留 16–20px；区域内标题到按钮可收至 6–8px。

## 4. 原创像素角色系统

### 4.1 角色语言

- 保留雨雨偏好的 **大头小身、大眼、飞行动势、高饱和服装、黑色像素轮廓**。
- 每个人必须有不同的发型、配色、职业道具和小性格，例如简历袋、小灯泡、放大镜、数据终端或唤醒棒。
- 可使用“像素飞行小队”的类型语言，但不使用现成动漫人物、品牌角色原图、标志性脸部细节或第三方版权标注。

### 4.2 排布规则

- 5 个角色建议采用 **右 3 / 左 2** 或 **左 3 / 右 2** 的不对称分布，形成 Z 字或对角视线，不要一字排开。
- 使用主角、中号贴纸、小号贴纸三档尺寸；相邻人物不要处于同一垂直线，也不要忽近忽远。
- 贴纸可以压住“机壳空边”，不能压住“功能内容”。每次出图后必须逐一检查按钮、文字、页脚和手机裁切边界。

### 4.3 素材技术红线

- 角色图必须是真实 RGBA 透明 PNG；棋盘格、白底或假透明背景不能进入页面。
- 像素素材显示时使用 `image-rendering: pixelated`，不使用会把边缘涂抹成精致插画的模糊滤镜。
- 导出前检查四边有透明安全区，角色脸部不偏黑、不被背景染色，也不带多余版权水印。

## 5. 动效语言

### 5.1 质感

**像素动效应该“跳”，而不是“漂”。**

- 优先使用 `steps()`、短位移、小旋转和回弹，避免丝滑漂浮、大面积呼吸光和过度游戏化特效。
- 循环动画必须有停顿，不能每一秒都抢用户注意力。引导箭头推荐节奏：**1.35s 一轮，下点 4px 两次后停顿**。
- 由用户操作触发的角色动画建议 360–560ms，每个角色使用不同的方向、位移和角度，不出现“有的跳、有的不跳”。

### 5.2 可用性

- 不通过动画改变按钮的真实点击区；动画元素应设置 `pointer-events: none`。
- 所有动画必须在结束后回到稳定状态，并通过 `prefers-reduced-motion` 提供静态降级。
- 发布前至少真实触发一次主 CTA、上一条、下一条、换壳和盲盒，不只看静态截图。

## 6. UX 规则

### 6.1 一次性娱乐工具

- 第一版只保留一个最直接的输入方式。如果粘贴文字已能完成价值，先不上链接读取、OCR、账号、相册或摄像头权限。
- 用户点开后 3 秒内可以开始玩；默认示例或盲盒可以帮助没有准备内容的用户立即体验。
- 功能增加的门槛：它必须明显提高“完成率、分享率或理解速度”，否则不为了显得功能多而加入。

### 6.2 长内容与结果

- 长文本允许页面纵向滚动，但单条结果优先保持在一块屏幕内阅读。
- 命中多条结果时使用“上一条 / 下一条”左右翻页，明确显示 `01 / 05` 进度，不在一个 LCD 中堆满长文。
- 没有命中时不输出假结果；给出可理解的空状态和一个可继续玩的示例。

## 7. 文案与网感

### 7.1 语气

- 像一个很懂中文职场语境、又敢说的同龄朋友；口语化、具体、带一点损，但不恶意给公司或岗位定性。
- 招聘方原话使用引号，让用户明确看到“对方说了什么”与“工具怎么翻译”。
- 先说人话，再给建议；不用先写一段安全声明、方法论或自我介绍。必要提示放到结果底部，一句足够。

### 7.2 好文案的标准

| 招聘方说 | 人话方向 |
| --- | --- |
| “Owner 意识” | 这个项目从头到尾都是你的责任，出了问题你背锅，成了功劳是团队的。 |
| “自驱力强” | 老板不叫你，你也要自己找活干。 |
| “Multi-task 能力强” | 你需要同时接住好几个活，而且每个人都会问你进度。 |
| “支持 Team 日常流程性工作” | 这一行就是打杂区，具体做什么要看当天群里谁 @ 你。 |
| “网感好” | 希望你 5G 在线，每一个热梗、KOL 和突然爆掉的话题都别落下。 |
| “Exposure 极高” | 你会很快被大老看见，也会很快被问“这页 PPT 怎么回事”。 |

判断一句话是否可用：**用户看完会不会说“对，就是这个意思”？** 如果只是更换了几个同义词，就还不够人话。

## 8. 从概念到发布的标准流程

### 8.1 必须遵守的协作顺序

1. **定义核心一句话**：用户输入什么，按什么，得到什么。
2. **先做 1 个 POC**：核心逻辑、文案和主交互跑通，不同时开发多个方向。
3. **先出模拟图，用户 OK 后再写回正式代码。** 调整排版或角色前，不一次性改动整个小工具。
4. **单变量迭代**：视觉、文案、功能分轮确认，每轮明确改了什么，避免互相污染。
5. **实装后重新截图**：不用模拟图替代成品验收，必须再从正式构建产物截一次图。
6. **最后才打包**：运行核心交互、移动端、透明图、权限与 ZIP 结构检查后，再产出发布包。

### 8.2 一票否决的视觉 QA

- 图片背景没有真透明，或人物四周仍有棋盘格。
- 角色被手机边缘截断成“半个人”，或遮挡任何文字、序号、箭头、输入区和按钮。
- 说“五个角色都会动”，但实际只检查了一两个；或只截静态图，没有真实点击验证。

### 8.3 小红书发布门禁

- ZIP 根目录只有一个 `index.html`，不多套一层文件夹，不打包预览页、测试页、`.DS_Store`、source map 或构建配置。
- 全部运行资源必须本地打包；无网络请求、外链字体、iframe、内联脚本、剪贴板 API 或容器禁用能力。
- ZIP 必须小于 10MiB，建议小于 2MiB。权限只勾选实际使用的相册、摄像头、麦克风或本地存储；没用就全部不勾。

## 9. 可复用的项目启动指令

将下方内容交给之后的 AI 助手或设计师：

> 请按《雨雨小红书小工具设计规范》设计这个小工具。先用一句话定义“用户输入—核心操作—可分享结果”，再选一个与功能有隐喻关系的 Y2K 复古实体作为主界面。视觉必须像素化、有彩色塑料感，避免苹果风毛玻璃和通用 AI 卡片。文案要具体、直接、有中文互联网语境，不写空洞黑话。默认以 402×874 手机首屏验收，主操作和一个次玩法尽量同屏露出。原创像素角色使用大头小身、飞行动势和不对称错落排布，只占机壳边角留白，绝不遮挡按钮或文字。实际修改前先输出 iPhone 模拟图，等我确认 OK 后才写回正式代码。实装后重新做视觉、遮挡、动画、窄屏和小红书 ZIP 合规检查，然后再交付。

## 10. 规范的使用方式

- 这是“家族相似性”规范，不是要求每个小工具复制同一台 BB 机。不同工具应该选择不同的复古物件隐喻。
- 可以改变主机壳、屏幕形式和角色阵容；不能丢掉“Y2K 实体感、像素角色、紧凑首屏、人话文案、先模拟后实装”五个核心特征。
- 每完成一个新工具，把新的成功规则补充进本文档，但不把某一页的偶然尺寸当成所有项目的永久标准。
